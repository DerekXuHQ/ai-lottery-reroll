# 接力：接收

你是一个新会话，要接手一个已经变傻的会话的工作。Reroll 已经把旧会话记录里的东西都提出来了，**是用代码提的，没经过模型**：用户说过的原话、碰过的文件和命令、版本基线。你的任务是把它变成一份简短、核对过的交接，同时不让这些原始材料塞满你自己的上下文。

**确认前的硬规则：只读。** 唯一能写的文件是 `HANDOFF.md`。用读文件的工具看文件。不运行测试、构建、脚本或项目代码。

## 1. 找到接力包

`.relay/` 下最新的文件夹（在项目根目录，或用户指定的位置），里面有 `RELAY.md`；Reroll 生成的还会有 `relay.json`。没有的话，告诉用户先在 Reroll 的「接力」页生成一个（云端会话用那一页上的复制提示词），然后停下。

没有 `relay.json`、标题写着「旧会话自己写的」：这个包**可信度低一档**。旧会话看不到原文的地方，第 2 节可能是转述。每条引用都当「大概是用户原话」，第 3–6 节对照 git 和文件逐条核对；只靠这个包才知道的用户规则，在第 4 步里列出来请用户确认。

**会话自己写的包**（用 Reroll「会话不在这台电脑上？」那段提示词生成的）：文件夹里是 `INDEX.md` + `lead.md`，可能还有 `children/`。`lead.md` 就当 RELAY.md 用，可信度同样低一档。先读 `INDEX.md`：它是名单表，写着派出过几个子会话、每个的回执（已收／重做后收／缺／lead 代写）。

**导出记录的包**（新版提示词生成的）：文件夹里是 `INDEX.md` + `export.py` + `raw/`。`raw/` 里是脚本导出的工作记录原文（JSON Lines，只留对话，已去掉思考内容和系统指令），不是模型写的，可信度和 Reroll 生成的包一样高：
- `raw/00-lead.jsonl`：lead（旧会话）自己的记录。最后一轮是交接指令本身，跳过。
- `raw/00-lead/`：lead 派出的子 agent 在交接前的记录。
- `raw/<编号>-<名字>.jsonl`：各子会话自己导出的记录。和 `raw/00-lead/` 里同一个子 agent 的记录重复时，以行数多、时间晚的为准。
- `raw/<编号>-<名字>.md`：第一行写着「模型自己写的」的是事实清单，低一档。
- `INDEX.md` 里「我知道的结果」是 lead 写的，只当地图。
读法：Claude Code 记录每行是一个 JSON，`type` 为 `user` 或 `assistant`，内容在 `message.content`；Codex 记录看 `payload`。用户原话是 `type: user` 且内容是文字（不是 `tool_result`）的消息，按出现顺序编号 `[#n]`，逐字引用。lead 的记录当作第 2 步的原始记录，按 2a–2b 提炼。

## 2. 提炼：能用子代理就用子代理

能开子代理（比如 Task / Agent 工具）的话，把 2a–2b 交给它，让它**只**交回写好的 HANDOFF.md 正文，你再把正文写进 `HANDOFF.md`。这样原始记录不进你的上下文，这正是换新会话的意义。开不了就自己做。

2a. 读完整个 `RELAY.md`。可信度：用户原话（第 2 节）和事实（第 3–6 节）优先；第 8 节是变傻的会话写的，只当地图，每条都要核对。如果整个包都是旧会话自己写的，第 2–7 节同样要这样对待。

2b. 写 `HANDOFF.md`（如果已有同名文件、且第一行不是 `# HANDOFF —` 开头，那是用户自己的文件：停下来问）。每条注明出处：用户消息写 `[#n]`，否则写文件路径。

```markdown
# HANDOFF — <任务>  (<日期>，来自接力包 <文件夹>)

## 真实目标
用户最终想要什么，怎样算成功。

## 最初的设想
一开始定方向的用户原话，引用并注 [#n]。

## 已确认的决定
- 决定 —— 原因 [#n]。后面改过的写：「原来是 X，后来改成 Y [#a → #b]」。

## 用户偏好与约束
所有规则、纠正和偏好（RELAY.md 里标 ★ 的），合并去重，只留仍然有效的。

## 当前状态
- 已完成并核实：
- 改了但没核实：
- 未提交 / 未保存：

## 产物与路径
`路径` —— 是什么（只列存在的；不存在的放进「未决问题」）。

## 死路（不要再试）
- 方案 —— 为什么不行（失败的命令、撤回的改动、用户否掉的）。

## 未决问题
## 下一步
1. 最具体的下一个动作
## 怎么验收
```

2c. **有 `children/`，或 `raw/` 里不止 lead 一份记录时（一个 lead 带着子会话）**：每个子会话的文件（`.md` 或 `.jsonl`）交给一个子代理，能并行就并行，一次最多 8 个，每个子代理只读一个文件。让它只交回半页：名字｜任务｜状态｜产出在哪｜下一步｜用户直接对它说的规则和纠正（逐字，注出处 `[名字#n]`）。不要自己读这些文件。拿到全部半页后，在 HANDOFF.md 里：
- 「用户偏好与约束」合并 lead 和所有子会话里的规则，去重；同一件事说法冲突的，以时间最晚的为准，并写明冲突。
- 「当前状态」前面加一张工作线总表，一个子会话一行：名字｜状态｜产出｜下一步｜回执。
- INDEX.md 里标「缺」的，单独列进「未决问题」：写名字、原因，以及「这部分工作没有交接过来」。
- 「lead 代写」的只当地图，不当事实。

## 3. 用你自己的工具对照现实核对

按 RELAY.md 第 6 节：

- **在 git 仓库里的文件**：在那个仓库里分别运行 `git status`、`git log --oneline -15`、`git diff --stat`（一条一条跑，不要串起来）。和生成接力包时记录的提交对比：之后改了什么、什么没提交、说「完成了」的是不是真的在。
- **不在 git 里的文件**（标 †）：把每个文件现在的大小和修改时间，和第 3 节记录的对比。一样 = 生成接力包后没动过；不一样或不见了，要说出来。
- **核对不了的**（服务器、账号、发布、别的电脑）：列进「需要你手动核对」。

现实和交接对不上的地方，改 HANDOFF.md，并注明改了什么。

## 4. 和用户确认

回复只包括：

1. 一句话真实目标
2. 不超过 10 行的要点清单（决定、偏好、下一步），让用户打勾、划掉或改
3. 第 3 步发现的对不上的地方
4. 只有用户能做的手动核对；有子会话标「缺」的，问用户要不要到那个子会话里单独打包
5. 你建议的下一步

等用户回复。用户改过的以用户为准，并更新进 HANDOFF.md。之后按 HANDOFF.md 工作；只有要查某条 [#n] 或某个文件时，才回去看 RELAY.md 或原始记录。
