# 交接

目的：让一个**完全没有本次对话记忆**的新会话，只读一份文件就能无缝接手。

## 原则

- **以文件和 git 为准，不以记忆为准。** 这个会话可能已经被污染，你对"做了什么"的印象不可靠。每一条"现状"都要通过实际查看文件、`git status`、`git diff`、`git log` 来确认。
- **记录死路比记录成果更重要。** 被否定过的方案、踩过的坑必须写清楚，并写上原因，防止新会话重蹈覆辙。
- **区分"用户确认过的"和"我自己推断的"。** 推断要标【推断】。
- 只写新会话需要的信息，不复述对话过程。

## 步骤

1. 运行 `git status`、`git diff --stat`、`git log --oneline -15`（不是 git 仓库就跳过），查看本次改动过的关键文件。只运行这些只读命令，每条单独运行，不要用 `&&`、`;` 或管道连起来。看文件用读取文件的工具，不要用 `cat`、`ls`。不运行测试、脚本、构建或项目代码。
2. 在项目根目录写 `HANDOFF.md`。这是本次唯一允许写入的文件。
   - 已存在且第一行以 `# HANDOFF —` 开头：是之前的交接，读一遍后整体更新。
   - 已存在但不是这个格式：那是用户自己的文件。**停下来问用户**，不要覆盖。
   结构如下：

```markdown
# HANDOFF — <任务名>  (<日期>)

## 真实目标
用户最终想达成什么（不只是字面任务）。成功的标准是什么。

## 已确认的决定
- 决定 —— 原因（用户确认 / 【推断】）

## 当前状态（已核实）
- 完成并验证过的：
- 改了但未验证的：
- 关键文件：`路径` —— 作用
- 未提交的改动：

## 死路（不要再试）
- 方案 —— 为什么不行

## 用户偏好与约束
本次对话里用户表达过的要求、习惯、不喜欢的做法。

## 未决问题
需要用户拍板的事。

## 下一步
1. 最具体的下一个动作
2. ...

## 验证方法
怎么确认任务完成：要跑的命令、要看的结果。
```

3. 如果有未提交的改动，问用户是否先 commit。**不要自己 commit。**
4. 最后只输出三样东西：
   - `HANDOFF.md` 的路径
   - 你最不确定的 1～3 条内容，请用户核对
   - 一行给新会话的启动语：`/pickup`（新会话也装了 pickup skill 时），否则用：`读 HANDOFF.md，核对 git 现状，复述目标和下一步，等我确认后再动手。`
